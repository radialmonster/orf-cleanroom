# Open questions

1. **Value assembly:** how q, H and L combine into a signed residual. No mapping tried so far beats the trivial baseline. To test: take tokens from several CC0 V1 files, tabulate (q, suffix) against neighbouring-pixel differences, and test candidate assemblies for consistency with a smooth image.
2. **Predictor:** which neighbours the residual is relative to. The horizontal-gradient lead (see the F1 lead, #11) needs testing by integrating along rows. To test: fit candidate predictors (left, up, mixtures, odd/even rows or columns) to partly assembled values; the right one gives a markedly narrower residual distribution.
3. **Row stride drift:** on some bodies the per-row token count drifts instead of staying equal to the width. Why? To test: list the manifest files with `row_stride` drift, measure per-row token counts, and check for row headers, padding or per-row byte alignment.
4. **Horizontal offset ramp:** the alignment offset with the preview grows with row band. Is that an artefact of the alignment method or real?
5. **Larger sensors:** the ordinary (non-escape) code in files sharing the 31-bit escape. Code-length statistics on larger-sensor files, compared with V1, would constrain it. Lead #37 found no q=30 (31-bit) escape in 11 CC0 files with the parse from #11 (escapes at q 17 to 29), so whether the escape exists in other files or needs a different parse is also open.
6. **Reproduction:** turn each finding into a script in `tools/` that runs on named CC0 files, and reproduce each other's leads (the open issues labelled `lead`; `python tools/findings_index.py` lists the verified findings). Good starting files for the F1 lead (#11) (5240-wide payloads): raw.pixls.us ids 6343 (OM-5), 8549 (OM-5 Mark II), and the 5240-wide E-M1MarkII files, all CC0.
7. **V2 classification:** which compressed manifest files belong to V2, or to some further variant, is not settled (their `variant` stays `unassigned`). To test: define a signature (payload width, bits per pixel, escape behaviour) in a `tools/` script, run it over all CC0 manifest files, and report which files it separates and how strongly.
8. **V0 pixel order inside a unit (spec S2.4, gap G4):** first-then-second (as emitted by the reference decoder) or swapped, for packed-12 and packed-12.8. Numbers so far, from `tools/unit_order_probe.py` on 14 CC0 files (packed-12 and 12.8): ratio A/W of the cross-unit to the within-unit lag-1 difference is 0.997 to 1.001 (all rows) for the emitted order and 1.000 to 1.063 for the swapped one; on edge-rich units only (threshold 300) emitted 0.97 to 1.08, swapped 1.004 to 1.278, and the swapped order is never smoother than the emitted one. This is in the right direction on every file but within 0.1 to 0.5% on 5 of the 14 (XZ-10, SH-2, SP570UZ, XZ-2, SP565UZ), so it is not decisive. To test: a file with a hard, sharp, vertical edge or a chart with fine horizontal detail (large cross-unit differences), or a derived relation between the two pixels of a unit and the known CFA colours (the pair must be R,G or G,B in that order across the row).
9. **V0 packed-16 byte order versus the TIFF byte-order mark (spec S4.2, gap G2):** E-1 and E-400 (`II`, little-endian) and E-10 (`MM`, big-endian) agree with the mark, 3 of 3. That cannot separate a rule from chance. To test: any packed-16 file from another body; report the mark and which order is smoother. Header `IIRS` vs `IIRO` on packed-12 separates the layouts 9 of 9 (lead #78) but is confounded with camera generation.
10. **E-400 interpolated pixels (lead #79):** 791 of 792 interior low-nibble words equal the floor of the mean of four same-colour neighbours; one interior word (y 2585, x 3681) matches neither the axial-2 nor the diagonal-1 family, and none of the mapped words falls on parity (1,1). To test: a second E-400 file or another E-series packed-16 body; does a neighbour that is itself mapped explain the exception, and does the defect list fall on only some sites?

## Hypotheses (unverified, not evidence)

- **H1: one shared decompression scheme across most compressed ORF bodies**, with per-model differences limited to dimensions, crop, levels, white balance and colour. Source: a general AI-assistant summary of unknown provenance, so it carries no weight here. Our own measurements so far show at least two bitstream behaviours (V1 and V2 in VARIANTS.md), and there may be many more (per model, firmware or mode). Open either way. To test: classify every manifest file and see whether V2 reduces to V1 under some parameter, or whether more variants appear.
- **H2: High Res Shot files need separate handling.** Source: vendor documentation that the mode exists. To test: measure their signature.
