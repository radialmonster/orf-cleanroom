# SPEC: V1 (calm-parse compressed ORF payloads)

Stub. Assembled only from verified findings and open leads. A statement that cites only a lead is **unverified** and marked so. No decoder exists for V1; the reference decoder (`decoder/orf_decode.py`) reports "not yet specified". Definition and signature: [VARIANTS.md](../VARIANTS.md#v1-calm-parse-compressed). This spec changes by new findings: when a lead is verified, replace its citation by the finding ID in a PR.

IDs used below (all in `findings/unassigned/`, because no manifest row is assigned to V1 yet):

- `F-em1` = `2026-10-19--radialmonster--em1mk2-token-dependence-vertical-lag2-differs`
- `F-b4b2` = `2026-10-20--radialmonster--em1mk2-b4-next-b2-share-provenance` (partial verification of lead #11)
- `F-tpp` = `2026-10-21--radialmonster--tokens-per-pixel-on-non-5240-bodies` (Partial verification of lead #29: item 2 only, tokens per pixel on five CC0 bodies, none 5240 wide; items 1 and 3 to 9 not verified)

## S1. Verified
- S1.1 Parsing the payload with the k=5 token model (q zero bits, stop bit, 5-bit suffix) consumes the whole payload to within 4 bits on every file tested in full, 6 of 6. The row period equals W where the row-start profile is sharp; busy bodies carry more than W tokens per row. [F-period]
- S1.2 On the four 5240-wide E-M1MarkII files (ids 1993, 1995, 1997, 1998), with the same token parse: dependence between neighbouring tokens is cross-field at lag 1 and 3 (H predicts the next L, L predicts the next H) and same-field at lag 2; the vertical lag-2 L-L dependence differs between files (0.017 to 0.018 bit on three, 0.0007 on id 1993). [F-em1]
- S1.3 With the same parse, b4 of one token carries 0.95 to 0.98 of the baseline-adjusted information between H of that token and L of the next, on E-M1MarkII ids 1993 (5240 wide) and 1994 (10400 wide), 400-row prefix and whole payload. The amount of that information differs by file: about 0.05 bit on id 1993, 0.09 to 0.11 bit on id 1994. [F-b4b2]
- S1.4 With the S1.1 parse (k=5, stop bit 1, escapes parsed like any token), whole payloads, tokens parsed divided by payload width x height is 1.027 to 1.036 on four CC0 files from bodies not 5240 wide (E-P3 and E-PM1 4080x3040: 1.0271, 1.0287; E-M1 4640x3472: 1.0363; E-M10 Mark IV 5200x3904: 1.0287) and 1.155 on TG-7 (4040x3016, 1.1552), the busiest of the five by bits per pixel. Escapes are 0.008% to 0.18% of tokens. Scope: Partial, item 2 of lead #29 on these five files only; the lead's calm 5240-wide figures (1.0001 to 1.0036) were not tested, and the E-M1 value is slightly outside the lead's 4640-wide range (1.025 to 1.034). [F-tpp]

## S2. Lead only (unverified)
- S2.1 The token parse itself (q zeros, stop bit, 5-bit suffix, escape at q >= 17) (the parse only; no reading of the residual is claimed). [lead #11, unverified]
- S2.2 No q=30 escape in 11 CC0 files with the parse from #11; escapes occur at q 17 to 29. A later run on 15 files agrees (q 17 to 28 plus isolated outliers; see [V2.md](V2.md) S2.2). [lead #37, unverified]

## Gaps
- G1. **Value assembly:** how q, H and L (labels for the bit groups b4b3 and b2b1b0) combine into a value. No signed or other reading of L is established by measurement. No mapping tried so far beats the trivial baseline. To test: take tokens from several CC0 V1 files, tabulate (q, suffix) against neighbouring-pixel differences, and test candidate assemblies for consistency with a smooth image.
- G2. **Predictor:** which neighbours the residual is relative to. No predictor is established; testing by integrating along rows is one way. To test: fit candidate predictors (left, up, mixtures, odd/even rows or columns) to partly assembled values; the right one gives a markedly narrower residual distribution.
- G3. **Row stride drift:** on some bodies the per-row token count drifts instead of staying equal to the width (S1.1 notes busy bodies exceed W). Why? To test: list the manifest files with `row_stride` drift, measure per-row token counts, and check for row headers, padding or per-row byte alignment. This may split the variant.
- G4. **Horizontal offset ramp:** the alignment offset with the preview grows with row band. Is that an artefact of the alignment method or real?
- G5. **Reproduction starting files:** good files for the #11 parse are the 5240-wide payloads: raw.pixls.us ids 6343 (OM-5), 8549 (OM-5 Mark II), and the 5240-wide E-M1MarkII files, all CC0.
- G6. Hypothesis H1: one shared decompression scheme across most compressed ORF bodies, with per-model differences limited to dimensions, crop, levels, white balance and colour (hypothesis, unverified; not evidence). Source: a general AI-assistant summary of unknown provenance, so it carries no weight here. Our own measurements so far show at least two bitstream behaviours (V1 and V2 in VARIANTS.md), and there may be many more (per model, firmware or mode). To test: classify every manifest file and see whether V2 reduces to V1 under some parameter, or whether more variants appear. See also [V2.md](V2.md).
- G7. Hypothesis H2, High Res Shot files need separate handling (hypothesis, unverified; not evidence), is recorded in [V0.md](V0.md) G5 but applies here too: 19 of the 21 High Res Shot files in the manifest are compressed. To test: compare the token parse and row stride of a High Res Shot file with a normal-mode file of the same body.
- G8. **Suffix width on TG-7:** in a whole-payload scan with suffix width k = 2 to 8, tokens per pixel is nearest 1 at k=5 (stop bit 1) on four of five files (1.027 to 1.036), but on TG-7 k=6 gives 1.0006 against 1.155 for k=5 [F-tpp]. Either TG-7 uses a different suffix width, or the k=6 value is coincidence, or the busy-body excess over one token per pixel (S1.1, G3) is what k=6 absorbs. The scan script was not committed. To test: a `tools/` version of the k scan; run it on TG-7 and other busy bodies and check whether the k=6 parse still consumes the payload to within a few bits (S1.1) and whether its escape count, q histogram and neighbour dependences (S1.2) look like a code or like noise.
- G9. **Lead #29 item 1 has no defined measure:** "only k=5 gives zero change in bits consumed per row" needs rows delimited in the token stream, and no row boundary is known (G3; `tools/orf_tokens.py` has no suffix-width option, F-tpp). Anyone taking item 1 must first define a per-row measure (for example how row starts are located and what "bits consumed per row" is counted from) and say how it works without row delimiters, before running k = 2 to 8 with both stop-bit conventions. Until then item 1 is untested; the whole-payload tokens-per-pixel scan of G8 is a different measure and neither confirms nor contradicts it (it does not separate the stop-bit conventions either: k=5 with stop 0 gives 0.973 to 0.999 on the four ordinary files).
